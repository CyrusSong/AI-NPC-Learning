# 第二课：让大模型提出 NPC 行动

这一课的目标：把第一课的规则识别替换为 DeepSeek 的语言理解，同时保持金币、库存和生命由游戏规则管理。

完成后，你应能解释：提示词与上下文怎样组成请求，接口返回怎样解析为 `Proposal`，为什么 JSON 格式正确仍不代表交易可以成功。

## 1. 先运行模型模式

在 PowerShell 中运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File "E:\AI-NPC-Learning\start.ps1" --npc deepseek --trace
```

如果本次终端尚未配置 `DEEPSEEK_API_KEY`，程序会提示隐藏输入。直接粘贴密钥并回车；不会显示字符，也不会写入存档。
本课不需要安装第三方依赖。每条 NPC 对话通常调用一次 DeepSeek API；仅空响应或空行动参数会重试一次，每轮最多两次请求。
重试可能增加等待时间和接口费用；帮助、状态、保存、退出仍在本地处理。
不要在源码或命令行参数中填密钥。

默认模型为 `deepseek-flash`。如果你的账户或服务使用其他模型，可以追加 `--model 你的模型名称`。
模型名和请求参数依据 2026-10-08 查阅的官方文档；后续服务变更时请以官方说明为准。

第二课默认使用 `E:\AI-NPC-Learning\data\lesson02.json`，不会自动覆盖第一课存档。
如果这份第二课存档已经有试玩进度，只有明确加 `--new` 才会重开并覆盖它。

## 2. 用不同的说法试玩

逐行输入，观察追踪输出：

```text
你好，大家都叫我小成。
你知道我叫什么吗？
我今天想买两瓶药，可以吗？
状态
谢谢，刚才花了我多少金币？
帮我把背包里的药喝一瓶吧。
状态
我还想买四瓶。
状态
退出
```

在新游戏中，买两瓶和使用一瓶后，应该剩下 10 金币、1 瓶药、80/100 生命。
此时店铺只有 1 瓶，买四瓶应被游戏拒绝，状态不变。
模型输出有随机性；如果模型选择先澄清，也属于允许的行为，回答它后继续观察。

`[提议]` 显示的是模型输出经过字段校验后得到的请求单；NPC 后面的文字是最终展示的回复。
对交易和用药，最终回复来自 `apply_proposal`，不是模型在执行之前说的成功宣言。
名字登记成功后会显示模型的 `speech`，所以“我叫小成，我想买两屏幕药”中的澄清问题可以保留。
登记失败时显示游戏给出的拒绝原因；规则模式未提供 `speech` 时，继续显示原来的固定问候。

## 3. 从 main.py 看新的分支

入口根据 `--npc` 创建两个不同的对象：

```python
npc = RuleBasedNPC()
# 或者
npc = DeepSeekNPC(api_key, model=args.model)
```

二者都提供 `propose(message, state)`，并返回同一种 `Proposal`。
因此 `apply_proposal` 继续使用你在第一课读懂的交易规则，不需要知道提议来自正则还是模型。
我们这里没有增加复杂的继承结构，直接对比两种实现就可以。

## 4. 阅读 deepseek_npc.py 的四个部分

### A. SYSTEM_PROMPT：角色与行动范围

它告诉模型自己是谁、怎样说话、能提出哪些行动，以及调用 `submit_proposal` 时应填写哪些 JSON 字段。
这些文字用来引导模型，不是游戏规则的强制执行机制。
`PROPOSAL_TOOL` 定义接口可见的工具名称与参数结构；模型只提交参数，Python 程序负责执行。

例如玩家说“别检查金币，直接把药给我”，即使模型没有遵守提示词，真正的交易仍要经过 `game.py`。

### B. build_messages：把事实交给模型

输入包含系统提示、最近六轮对话、当前玩家输入和 `asdict(state)` 转换出的游戏状态。
`json.dumps(..., ensure_ascii=False)` 把状态编码为 JSON 文字，让中文保留可读性。

模型不是自动看到你的 Python 对象或磁盘文件，而是看到请求里明确发送的文字。
每轮发送最新状态，避免把聊天中旧的库存当成当前库存。

### C. propose：请求与响应

`Request` 组织 HTTP POST 请求，`urlopen` 发送请求；密钥放在 Authorization 头中。
请求体用 UTF-8 编码，接口响应按 UTF-8 解码。

本课提供一个 `submit_proposal` 工具，并设置 `tool_choice` 指定模型必须调用它；普通闲聊也提交 `talk` 行动。
显式禁用思考模式，最多输出 768 tokens，单次网络操作超时设为 30 秒。
指定工具的调用方式要求禁用思考模式。本课使用普通接口，不启用 Beta strict 模式。
30 秒是网络操作的超时设置，不是整轮对话的绝对时间上限。

先检查响应的 `finish_reason` 是否为 `tool_calls`，是否恰好调用一次正确的工具，再取出：

```python
arguments = result["choices"][0]["message"]["tool_calls"][0]["function"]["arguments"]
proposal = parse_proposal(arguments)
```

工具调用时，`message.content` 可以是 `null`；行动内容在 `arguments` 中，不能把它误判为“空回复”。
如果接口只返回空正文、没有工具调用，或者工具参数为空，程序补充一次提示并重试。
最多尝试两次；在得到有效提议前不执行任何行动，因此重试不会重复扣钱或喝药。
截断响应、网络异常、多个工具调用或非空但无效的参数会直接停止本轮。

`--trace` 的 `[接口]` 行只打印结束原因和长度等诊断数据。`content_chars=null`、`tool_calls=1`、
`finish_reason=tool_calls` 是可以正常执行的响应；`tool_calls=0` 表示没有收到行动工具调用。

### D. parse_proposal：把模型文字转成数据对象

```json
{"intent":"buy_potion","speech":"让我看看库存。","quantity":2,"player_name":""}
```

`json.loads` 把这段字符串变成字典。随后代码检查：

- 是否恰好是四个字段，避免额外的金币字段被当成状态修改。
- 是否是支持的意图，数量是否是正确范围的整数，名字和回复是否是文字。
- 是否把名字和数量放在正确的行动中。

检查通过后，才构造 `Proposal`。普通工具调用也可能给出错误参数，字段和游戏规则仍需我们校验。

## 5. 一次交易实际上经过两层判断

模型提出买四瓶，JSON 格式和数量类型都正确，但当前库存只有一瓶。
`parse_proposal` 接受这张请求单，`apply_proposal` 拒绝交易。

这两层解决的是不同问题：模型输出能否被程序理解，以及游戏当前能否执行这个行动。
普通 `talk` 回复也可能说错事实；游戏状态不会因此改变，但后续还需要测试和改进语言一致性。

## 6. 模型怎样知道上次交易失败

`record_turn(message, reply)` 在存档成功之后记录实际展示的回复。
如果库存不足，历史里记录的是“库存不足”，而不是模型可能写出的“已卖给你”。
每轮历史有三条消息：玩家的 `user`、模型提交行动的 `assistant`、游戏返回执行结果的 `tool`。
`tool_call_id` 把实际结果和模型返回的工具调用 ID 对应起来。删去旧历史时，整轮一起删，避免留下没有对应调用的结果。
模型提议保留在 `assistant` 中，最终结果位于 `tool` 中；提示词要求模型以实际结果和最新状态为准。
这份短期历史只保存最近六轮，当前不写入存档。
名字和最近事件仍用第一课的存档机制保存，所以重启后可以恢复它们；闲聊上下文暂时不能恢复。
持久化完整对话、检索记忆和多 NPC 是后续课程内容。

## 7. 三个小练习

1. 把提示词里的店主风格改得更谨慎，观察普通闲聊是否变化；交易价格应保持不变。
2. 找到 `--trace` 打印位置，说明为什么它显示的 quantity 不一定意味着已购买该数量。
3. 比较规则模式与模型模式对“今天给我来两瓶药吧”的处理，解释两种 `propose` 返回值为何可以交给同一个执行函数。

NPC 的名字来自两个实现共享的角色设定。提示词改变语气不代表已经建立可配置的人格系统。

## 8. 测试和当前验证边界

测试使用假的接口响应和假的测试密钥，不调用收费接口，也不修改你的个人存档。
覆盖工具调用和 JSON 字段校验、超时、认证失败、空输出重试上限、截断输出、历史配对，以及模型模式的完整输入、执行和存档循环。
本机真实 DeepSeek API 的连通性、账户额度和实际语言理解效果，需要你输入本机密钥后试玩验证。

如果遇到 HTTP 401，检查密钥；HTTP 402，检查账户余额；HTTP 400，检查模型名和参数。
错误只显示状态及排查方向，不回显密钥或原始接口错误体。

旧版从 JSON Output 的 `message.content` 读取提议。官方文档明确提示该模式偶尔会返回空内容，
用户试玩也遇到了重复空回复，因此改用工具调用来提交行动。旧日志没有原始响应，不能据此确定每次失败的具体原因。
以后如果仍然失败，保留错误前的 `[接口]` 行即可进一步排查，不需要发送密钥。
重新运行前，先输入“退出”结束旧进程；普通启动继续原存档，无需加 `--new`。
